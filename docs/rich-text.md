# Telegram Rich Text: правила гостевого агента

Проверено по официальному Telegram Bot API 10.4, 11 ноября 2026 года.
Нативные Rich Messages отличаются от обычного `sendMessage` с `parse_mode`.
Гостевой агент возвращает поддерживаемый Markdown, sidecar собирает `blocks`
и отправляет их через `sendRichMessage` / rich-вариант `answerGuestQuery`,
а затем редактирует тот же ответ через `editMessageText.rich_message`.

Правила находятся в `rich_renderer.RICH_TEXT_POLICY` и добавляются в transport
instructions **каждого** запроса: Hermes Runs и Chat Completions, новый диалог
и продолжение существующего. Отдельная отправка ответа через Userbot не нужна:
она создаст дубликат. Userbot используется для явно запрошенных действий и QA.

## Выбирать оформление по содержанию

| Содержание | Формат | Ограничение качества |
| --- | --- | --- |
| Короткий ответ, один факт | Обычный абзац | Без искусственного заголовка |
| Несколько смысловых разделов | `##` и `###` | Заголовки описывают содержание, уровни идут последовательно |
| Сравнение вариантов по одинаковым полям, цены, лимиты, замеры | Нативная таблица | Обычно 2–4 коротких колонки, единицы в заголовке |
| Последовательность действий | Нумерованный список | Один шаг — одно действие |
| Параллельные факты | Маркированный список | Короткие самостоятельные пункты |
| Задачи с известным статусом | `- [ ]` / `- [x]` | Не превращать объяснение в чеклист |
| Ключевой результат | `**полужирный**` | Отдельная фраза, не весь абзац |
| Термин или мягкий акцент | `*курсив*` | Умеренно |
| Исправление / особо важный результат | `~~старое~~` / `==важное==` | Только с соответствующим смыслом |
| Идентификатор, команда, код | Inline code / fenced code | Код остаётся буквальным |
| Источник | Ссылка с понятной подписью, сноска | Точный URL, без выдуманных источников |
| Настоящая цитата | `>` | Автор или источник указан рядом |
| Длинная необязательная цитата | Expandable blockquote | Не использовать как обычный раздел |
| Необязательные подробности | Details с понятным summary | Ответ и существенные оговорки остаются снаружи |
| Намеренно скрываемые слова | `||спойлер||` | Маскирует слова, не сворачивает раздел |
| Формула | `$$E=mc^2$$` отдельной строкой | Inline `$math$` текущий renderer не поддерживает |
| Реальное изображение или файл | Media-блок | Проверенный источник; не заменять таблицу картинкой |

Это редакционные правила проекта. Они не являются дополнительными лимитами API.
У Telegram: 32768 символов, 500 блоков с учётом вложенных элементов и строк таблиц,
16 уровней вложенности, 50 медиа и до 20 колонок в таблице. Sidecar имеет более
узкие ограничения длины ответа. Не пытаться заполнить лимит ради оформления.

## Таблицы

```markdown
| Тариф | Цена, ₽/мес. | Лимит, ГБ |
|:---|---:|---:|
| Старт | 100 | 1 |
| Плюс | 200 | 5 |
| Про | 300 | 10 |
```

Таблицу писать непосредственно в ответе, без внешнего code fence. В примере
выше fence нужен только для показа исходного синтаксиса в документации.
Строка разделителей обязательна. `:---`, `:---:`, `---:` задают выравнивание.
В ячейке разрешено inline-оформление; длинные объяснения, списки и отдельные
абзацы нужно вынести ниже. Буквальный pipe записывать как `\|`; pipe внутри
code span сохраняется. Renderer выставляет `is_compact`, границы и полосы.

Если полей много, разделить сравнение по темам или дать список карточек.
Если текст всё же содержит больше 20 колонок, renderer сохраняет его целиком
как preformatted block, чтобы Telegram не отклонил всё сообщение.

## Подробности и буквальный текст

```markdown
Главный вывод и существенная оговорка видны сразу.

<details><summary>Как получен результат</summary>

Первый абзац.

Второй абзац с **акцентом**.

- Дополнительная деталь
- Ещё одна

</details>
```

Без `open` раздел свёрнут. `<details open>` начинает его раскрытым.
Пустая строка разделяет абзацы; обычный перенос строки не создаёт новый блок.
Details могут содержать поддерживаемый Markdown, в том числе вложенные details.
Цитата использует `>`, длинная сворачиваемая цитата — отдельные строки
`<blockquote expandable>` и `</blockquote>`.

Markdown-символы можно экранировать обратным слешем. Код в backticks и fenced
code остаётся буквальным. Для inline-кода с одиночным backtick внутри можно
использовать двойные backticks. Ссылки: `[Telegram](https://core.telegram.org/bots/api)`;
пробелы и скобки внутри URL следует percent-encode.

Media-синтаксис `![подпись](URL "caption")` распознаёт картинки, GIF, видео
MP4/MOV/WebM, аудио MP3/M4A/AAC/FLAC, voice notes OGG/OGA/Opus и документы
PDF/ZIP по расширению пути URL. Для прочих документов использовать обычную
ссылку или локальный MEDIA-файл. Collage/slideshow с отдельными media-строками
внутри `tg-collage` / `tg-slideshow` и карты с проверенными координатами уместны
по запросу, когда реально помогают ответу.

## Возможности транспорта и проверка

Renderer поддерживает ограниченный Markdown и inline HTML (`b`, `i`, `u`, `s`,
`code`, `mark`, `sub`, `sup`, `tg-spoiler`, `a`, `tg-emoji`), details, expandable
quotes, списки, сноски, display math, media, collage/slideshow и карту `tg-map`.
Это не полный HTML-парсер: HTML-таблицы/списки, CSS, произвольные embed, кнопки,
widgets, inline math и новые API-конструкторы нельзя обещать по одному лишь
наличию в документации Telegram. Если rich delivery выключена, агент получает
отдельные инструкции для обычного текста и списков.

Для QA недостаточно HTTP `ok` или плоского текста. Через штатный Userbot нужно
читать конкретный ответ с проверкой chat/message/sender, гидратировать `part`
через существующий reader и сравнивать native tree: порядок блоков, paragraphs,
heading levels, table rows/cells/alignment, list item boundaries, styles, details
children/open state, ссылки и расположение медиа. Нельзя подменять эту проверку
поиском подстроки в preview. Фактическая ширина, отступы и внешний вид на телефоне
требуют отдельной визуальной проверки на клиенте.
